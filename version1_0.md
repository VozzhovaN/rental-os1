ТЗ — Фиксация бизнес-архитектуры Rental-OS

Версия: 1.0
Дата: 02.09.2026
Проект: rental-os
Среда: Next.js + TypeScript + Prisma + SQLite
Назначение документа: зафиксировать архитектуру CRM перед дальнейшей разработкой.

1. ГЛАВНОЕ АРХИТЕКТУРНОЕ РЕШЕНИЕ

Rental-OS должен состоять из трёх независимых бизнес-контуров:

Посуточная аренда
Долгосрочная / помесячная аренда
Продажа недвижимости

При этом существующий Property является базовым физическим объектом недвижимости, но его коммерческая деятельность, рекламное описание, клиенты, бронирования и публикации должны относиться к соответствующему бизнес-контурy.

Критически важно

Не объединять посуточную аренду, долгосрочную аренду и продажу в один общий Dashboard.

Не использовать одну универсальную рекламную карточку для всех трёх режимов.

Не смешивать:

посуточное бронирование;
долгосрочную аренду;
продажу;
покупателей;
рекламные описания;
календари.
2. БАЗОВЫЙ ОБЪЕКТ Property

Существующая сущность Property сохраняется.

Она представляет физический объект недвижимости, а не конкретное рекламное объявление.

Например:
Property #15

2-комнатная квартира
55 м²
Ялта
ЖК ...
Property не должен превращаться в рекламное объявление.

В нём хранятся базовые фактические характеристики объекта, необходимые CRM.

3. КОНТУР №1 — ПОСУТОЧНАЯ АРЕНДА

Это существующий операционный контур Rental-OS.

Основные сущности
Property
   ↓
Booking
   ↓
Guest
   ↓
Dashboard / Calendar
   ↓
Sales Channels

Источник истины по занятости:

Property + Booking

Не создавать отдельную сущность календаря занятости.

4. ПОСУТОЧНЫЙ DASHBOARD

/crm/dashboard

Dashboard должен отображать только посуточную операционную деятельность.

В Dashboard не должны попадать:

объекты долгосрочной аренды;
объекты продажи;
рекламные карточки долгосрочной аренды;
рекламные карточки продажи;
покупатели;
сделки продажи.

Dashboard продолжает работать на основании существующих:

Property
Booking
Guest
SalesChannel
ChannelListing

и существующей логики календаря.

Не ломать существующий Dashboard.
5. ПОСУТОЧНЫЙ АВИТО

Для посуточной аренды используется уже реализованный интеграционный слой.

Архитектура:

CRM Property
     │
     ▼
ChannelListing
     │
     ▼
Существующее объявление Авито
     │
     ▼
AvitoAdapter
     │
     ▼
Календарь / бронирования Авито
Не создавать заново объявление Авито.

На данном этапе предполагается, что объявление уже существует на Авито.

CRM должна позволять:

подключить объявление;
привязать объявление к Property;
синхронизировать календарь;
получить внешнее бронирование;
отключить связь;
снова подключить связь.
6. ОТКЛЮЧЕНИЕ ОБЪЕКТА ОТ АВИТО

В карточке Property должен существовать отдельный блок:

Авито — посуточная аренда

Состояния:

Подключено
Отключено
Ошибка
Не подключено

Пользователь должен иметь возможность:

[Отключить от Авито]

и:

[Подключить к Авито]

При отключении:

НЕ удалять:

Property;
Booking;
Guest;
историю;
ChannelListing как историческую связь.

Отключается именно активность интеграции/синхронизации.

Причина:

собственник может временно снять объект с аренды, а затем вернуть его.

7. КОНТУР №2 — ДОЛГОСРОЧНАЯ АРЕНДА

Создать отдельный раздел основного CRM-меню:

«Долгосрочная аренда»

Долгосрочная аренда означает:

помесячная / среднесрочная / долгосрочная аренда в зависимости от условий бизнеса.

Объекты в этот раздел не добавляются автоматически.

Пользователь вручную выбирает существующий Property.

Например:

Долгосрочная аренда
        ↓
[+ Добавить объект]
        ↓
Выбор Property
        ↓
Создание карточки долгосрочной аренды
8. ДОЛГОСРОЧНЫЙ ОБЪЕКТ НЕ РАВЕН ПОСУТОЧНОМУ ОБЪЕКТУ

Один и тот же физический Property может присутствовать одновременно:

Посуточная аренда
+
Долгосрочная аренда

но рекламные карточки должны быть независимыми.

Например:

Property #15
      │
      ├── Посуточная аренда
      │      └── посуточное объявление
      │
      └── Долгосрочная аренда
             └── долгосрочная рекламная карточка

Изменение текста долгосрочной рекламы не должно менять описание посуточной рекламы.

10. РЕДАКТИРУЕМОЕ ОПИСАНИЕ ДОЛГОСРОЧНОЙ АРЕНДЫ

Это обязательная функция.

Пользователь должен самостоятельно редактировать рекламный текст.

Цель:

изменять маркетинговую подачу объекта в зависимости от ситуации и спроса.

Например:

Обычное объявление

65 000 ₽/месяц

или:

СПЕЦИАЛЬНОЕ ПРЕДЛОЖЕНИЕ

60 000 ₽/месяц
при аренде от 6 месяцев

Редактирование должно позволять менять:

заголовок;
текст;
акценты;
преимущества;
специальное предложение;
цену;
условия аренды.

14. ПРОДАЖА — НЕ ЧАСТЬ ПОСУТОЧНОЙ CRM

Объект, добавленный в продажу:

не должен появляться в Dashboard;
не должен создавать Booking;
не должен влиять на календарь посуточной аренды;
не должен попадать в KPI посуточной аренды.

Продажа является самостоятельным бизнес-контуром.

19. ИНТЕРЕСЫ КЛИЕНТА

Не связывать клиента и объект отношением «один к одному».

Использовать промежуточную сущность.

Рабочее название:

BuyerInterest

Архитектура:

Buyer
  │
  ├── BuyerInterest → Property/SaleListing #1
  │
  ├── BuyerInterest → Property/SaleListing #2
  │
  └── BuyerInterest → Property/SaleListing #3

Это позволяет:

одному клиенту интересоваться несколькими объектами;
одному объекту иметь нескольких потенциальных покупателей.
20. СТАТУСЫ ИНТЕРЕСА

24. ИСТОРИЯ КЛИЕНТА

10.09 — внесён задаток
20.09 — покупка

История должна быть хронологической.

30. ЧТО НЕЛЬЗЯ ДЕЛАТЬ В РАМКАХ ЭТОЙ АРХИТЕКТУРЫ

Cursor не должен:

переделывать существующий Dashboard без необходимости;
помещать долгосрочные объекты в Dashboard;
помещать объекты продажи в Dashboard;
создавать отдельный календарь для долгосрочной аренды без бизнес-требования;
создавать отдельный календарь продажи;
смешивать Booking и продажные сделки;
использовать Guest вместо покупателя;
превращать Property в рекламное объявление;
хранить все рекламные описания в Property;
создавать новое объявление Авито для существующего посуточного объявления;
создавать дубликаты Property;
создавать дубликаты объявлений;
удалять Property при отключении размещения;
удалять историю клиента;
добавлять новые модели без проверки существующей Prisma-схемы.

34. КРИТЕРИЙ ГОТОВОЙ АРХИТЕКТУРЫ

Архитектура считается реализованной корректно, если один и тот же физический объект может одновременно выглядеть в системе следующим образом:

Property #15
│
├── ПОСУТОЧНО
│   ├── активен
│   ├── Авито подключено
│   └── календарь работает
│
├── ДОЛГОСРОЧНО
│   ├── добавлен вручную
│   ├── цена 65 000 ₽
│   ├── своё описание
│   └── Авито / ЦИАН / Домклик
│
└── ПРОДАЖА
    ├── цена 18 900 000 ₽
    ├── своё описание
    ├── свои фотографии
    └── Авито / ЦИАН / Домклик

При этом:

Dashboard видит только посуточную часть.

А раздел:

Продажи → Клиенты

может показывать:

Покупатель
   ↓
Объект
   ↓
Показ
   ↓
Задаток
   ↓
Покупка / отказ
Финальное правило архитектуры

Я бы отдельно выделил его в начале документа для Cursor:

НЕ ПЫТАТЬСЯ СДЕЛАТЬ ИЗ PROPERTY УНИВЕРСАЛЬНОЕ ОБЪЯВЛЕНИЕ.

Property — физический объект недвижимости.

Посуточная аренда, долгосрочная аренда и продажа — три самостоятельных бизнес-контура со своими карточками, описаниями, фотографиями, ценами, клиентами и логикой работы.

Они могут ссылаться на один Property, но не должны смешивать свои бизнес-процессы.

Dashboard относится только к посуточной аренде.

Долгосрочная аренда и продажа имеют отдельные разделы.

Интеграционный слой является общим техническим механизмом, но конкретные сценарии публикации и синхронизации для каждого контура различаются.
